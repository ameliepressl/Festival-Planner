Programme planning

FA01 · Manage the artist catalogue

Add, edit and remove artists, including names, genres, default fees, colours and set lengths. The optional artist library copies entries into the editable festival catalogue. Clearly show when an artist already has performances planned. No minimum catalogue size is required.

FA02 · Schedule performances and operational blocks

Choose the festival day, stage and exact start minute. Each performance has its own agreed fee, duration, tentative or confirmed status, private notes and optional changeover. Grey blocks reserve time for breaks and other work without booking an artist. Linked changeovers move with the associated performance.

FA03 · Review the timetable and budget

Use a daily timetable or view all festival days. Show start and end times, appointment details, performance count, stage count and the artist budget: total, spent and remaining. Appointment details are also available by opening the appointment.

FA04 · Revise the programme safely

Edit and remove appointments. Validate edits as replacements rather than extra bookings. Reject invalid edits without changing the previous valid data. Catalogue changes update defaults for future bookings; existing performances retain their agreed fee and duration.

FA05 · Finalise, export and reopen

Finalisation validates the existing appointments without requiring a minimum number of artists or performances. The lineup remains read-only until reopened as a draft. Print or save a PDF with public or internal details, and export or restore a lineup JSON backup. These exports are not complete backups of every festival section.

Current lineup rules

  1. Configurable event: choose festival dates and opening hours, 1–12 stages and a non-negative artist budget. Appointments must fall within the selected festival day and stage hours. Saved per-day and per-stage hours are respected.
  2. Minute precision: start times and durations use whole minutes; 15:11 is a valid start time. A performance, including its changeover, must finish within the available hours.
  3. Stage conflicts: appointments on the same stage cannot overlap. Adjacent appointments are allowed. Conflict messages identify the existing appointments and when they end.
  4. Artist conflicts: an artist cannot perform overlapping sets on different stages. Different artists may perform at the same time on different stages.
  5. Repeat bookings: the same artist may perform more than once after a warning and confirmation. Each performance contributes its own agreed fee.
  6. Flexible budget: spending above the artist budget is allowed after confirmation when a change creates or increases the overrun. The remaining amount is then negative and shown in red. Removing a performance releases that performance's fee.
  7. Finalisation: no minimum booking count applies. A final lineup must pass its appointment checks and can only be edited after reopening.
  8. Persistence: accepted changes must remain consistent after reload. A failed browser write must report the problem and retain the previous saved state; a failed cloud save must not be described as successfully synced.

Shared festival workspace

Overview brings together festival facts, finances, project tasks and a readiness score. Project tasks support groups, subtasks, assignments, progress and dates relative to the festival. Task editing offers Save and Cancel. Readiness issues link to their source and appear on the task board without duplicating manually entered tasks.

The site map supports facilities, custom maps, layout checks, manual Save changes, Undo and Discard. Active stages must agree with the lineup. Crowd density and evacuation estimates show assumptions and the selected exit for each stage. Vendors contribute pitch income and visitor-needs checks; finances combine the saved planning assumptions and programme costs. The final checklist tracks event-day checks.

Supabase handles accounts and stores festivals. The browser keeps a local working copy of separate festival sections. Owners and invited members have role-based access: Owner and Admin manage protected details, finances, assignments and membership; Editors update permitted planning sections and task progress; Viewers read the plan. Database rules must enforce these permissions, not just the visible buttons.

An account can own several festivals and join shared festivals. Switching festivals must keep their data separate and ask about unsaved drafts. Successful sign-out removes the browser's festival copy. Section-based cloud saves reduce interference between teammates; simultaneous edits to the same section can still overwrite one another and are not live collaborative editing.

Current acceptance checks

A1 · Conflicts and adjacent appointments

A 16:00–17:00 performance blocks an overlapping appointment on that stage. A 17:00 start is accepted if it fits the opening hours and any reserved changeover.

A2 · Different stages and repeat artists

Different artists can play simultaneously on different stages. The same artist cannot overlap across stages, but can play another non-overlapping set after confirmation.

A3 · Event boundaries and precise times

Check the selected day and stage hours, including a set starting at 15:11. Reject an appointment outside the available hours without replacing valid saved data.

A4 · Budget confirmation

With €9,000 committed against a €10,000 budget, a €1,000 performance fits. A €1,001 performance requires confirmation of the €1 overrun. Cancelling keeps the original plan.

A5 · Edit, remove and retry a failed save

A conflicting edit preserves the previous appointment. A valid edit counts the fee once. A failed write keeps saved data unchanged and permits retry; removal frees the reserved time and performance fee.

A6 · Reload, finalise and permissions

Reload retains the saved programme and totals. Any valid booking count can be finalised. Final lineups stay read-only until reopened, and account roles restrict edits consistently across screens and database writes.

Boundaries and verification

The app is a planning tool. It does not sell tickets, pay artists, place real bookings or provide certified crowd-safety advice. Library prices, capacity rules and evacuation times are planning estimates. Professional event-safety review is required for real-world use.

Sign-in and cloud saving require Supabase. Optional external images may fail without preventing text-based planning. Tests use local data and mock services; passing them does not establish that the deployed database policies, every browser or all concurrent edits work. Live role and recovery checks are separate release checks.

Two-factor authentication is outside the agreed scope. Teaching-staff approval for the browser JavaScript stack is still unconfirmed. See the repository README and progress log for setup, validation evidence and outstanding deployment actions.
